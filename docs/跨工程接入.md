## 1. 工具解决什么问题

LGK-Vector 是一个本地桥接工具。它帮助人或 Codex 对 Vector DaVinci ECUC 工程执行以下操作：

- 找到某个 BSW 模块实际使用的 ECUC ARXML；
- 查询当前 SIP 中 container、parameter 和 reference 的定义；
- 在 DaVinci GUI 打开时，只读查看已经保存到磁盘的 ECUC 容器和值；
- 定位真实容器及其行号范围；
- 对已经确认的位置执行最小行范围修改；
- 获取 DaVinci 校验错误；
- 在明确确认后调用 DaVinci 自动求解；
- 生成受影响模块或全部模块的 C/H/LSL；
- 复用并正常关闭 resident host。

LGK-Vector 不携带 DaVinci、Vector SIP、许可证或客户工程。它运行的前提是，本机已经具备合法可用、并且与目标工程匹配的 Vector 环境。

工具不绑定 TC275，也不把模块路径固定成 `/MICROSAR/...`。它从目标 DPA 和 ECUC 中读取真实模块文件及 `ECUC-MODULE-DEF` 路径，因此同一套程序可以服务不同 MCU 和不同供应商资源包；具体工程能否生成，仍由该工程、DaVinci 版本和 SIP 的兼容性决定。

## 2. 全局共享安装

### 2.1 唯一中央目录

整台电脑只保留一份源码、程序、Skill、测试和更新记录：

```text
D:\Tools\LGK-Vector\
├─ SKILL.md
├─ Cargo.toml / Cargo.lock
├─ src\
├─ scripts\
├─ tests\
├─ docs\
├─ CHANGELOG.md
└─ target\release\
   ├─ lgk-vector.exe
   └─ lgk-vector-host.exe
```

不要在每个 AUTOSAR 工程中复制一套 `Vector\LGK-Vector`。中央目录只有一个 Git 仓库，任何工程中发现并修复的工具问题都会集中到这里，其他工程下次调用时自动使用新版本。

### 2.2 编译程序

第一次取得源码，或者修改了 Rust 源码后，在中央目录执行：

```powershell
Set-Location "D:\Tools\LGK-Vector"
cargo test --all-targets --locked
cargo build --release --locked
```

包装器优先使用中央目录根部的发布程序；根部没有时，自动使用 `target\release\lgk-vector.exe` 和同目录的 host。

### 2.3 安装 Codex Skill

Codex 需要在用户 skills 目录中看到 `lgk-vector`。不要复制源码，运行安装脚本建立 Windows Junction：

```powershell
& "D:\Tools\LGK-Vector\scripts\Install-LGKVectorSkill.ps1"
```

默认结果：

```text
C:\Users\<用户名>\.codex\skills\lgk-vector
    → D:\Tools\LGK-Vector
```

左边只是目录链接，不是第二份源码。Codex 无论当前打开哪个工程，触发 `$lgk-vector` 后看到的都是 D 盘中央源码。

如果 skills 目录不同，可以显式指定：

```powershell
& "D:\Tools\LGK-Vector\scripts\Install-LGKVectorSkill.ps1" `
  -SkillPath "C:\Users\UserName\.codex\skills\lgk-vector"
```

如果目标位置已经是普通目录，脚本会停止并提示检查，不会覆盖其中内容。

## 3. 新工程接入

### 3.1 每个工程只增加一个配置文件

在目标工程真正的 DaVinci Cfg 目录创建 `lgk-vector.json`：

```json
{
  "tool_path": "D:\\Vector\\SIP"
}
```

- `project_path`：新工程可省略，工具会使用 `lgk-vector.json` 所在目录；若保留旧字段，则必须是同一目录的绝对路径；
- `tool_path`：本机实际可用的 Vector SIP/工具根目录。

如果 Cfg 目录有多个 `.dpa`，或工具目录能找到多个 `DVCfgCmd.exe`，明确指定：

```json
{
  "tool_path": "D:\\Vector\\SIP",
  "project_file": "Vehicle.dpa",
  "davinci_command_path": "D:\\Vector\\DaVinci\\Exec\\DVCfgCmd.exe"
}
```

`project_file` 必须是当前 Cfg 目录内的 `.dpa`，可使用相对路径。`davinci_command_path` 必须直接指向 `DVCfgCmd.exe`；相对路径按 `tool_path` 解析。

也可以让初始化脚本生成配置并立即做完整的静态预检：

```powershell
& "D:\Tools\LGK-Vector\scripts\Initialize-LGKVectorProject.ps1" `
  -ProjectPath "D:\Work\ProjectA\Cfg" `
  -ToolPath "D:\Vector\SIP"
```

旧工程的 `LGK_project_path` 和 `LGK_tool_path` 继续兼容；新工程使用小写字段。

### 3.2 第一次只做预检

```powershell
& "D:\Tools\LGK-Vector\scripts\Invoke-LGKVector.ps1" `
  -ProjectPath "D:\Work\ProjectA\Proj_Config\Bsw_Config\Cfg" `
  -Request '{"func":"find_module","module":"Com"}' `
  -ValidateOnly
```

`-ValidateOnly` 通过 Rust doctor 检查：

- 请求 JSON 是否有效；
- 函数名是否支持；
- `lgk-vector.json` 是否存在；
- CLI 与 Host 版本是否一致；
- 请求必填参数是否完整；
- 工程路径、工具路径、唯一 DPA 和唯一 `DVCfgCmd.exe` 是否有效；
- 只读请求能否在当前 DPA/ECUC/BSWMD 上真正解析。

它不启动 resident host，不打开 DaVinci，也不修改工程。因此 `valid=true` 只表示静态前置条件成立，不证明许可证、DPA 锁、DaVinci 启动或真实生成已经成功；这些要在合法且可丢弃的集成测试工程中验证。

## 4. 两种使用方式

### 4.1 直接让 Codex 使用

在任意 AUTOSAR 工程对话中可以这样说：

```text
使用 $lgk-vector 检查本工程 COM 模块中的 ComSignal，先只读，不修改。
```

或者：

```text
使用 $lgk-vector 修改 ComBitPosition。修改前查参数定义和当前值，定位准确容器，只生成 Com，最后正常关闭 host。ECUC 修改和生成代码分别说明。
```

Codex 会通过全局 Junction 读取中央 Skill 和源码。目标工程路径仍由该工程自己的 `lgk-vector.json` 决定。

### 4.2 手工调用 PowerShell 包装器

通用格式：

```powershell
& "D:\Tools\LGK-Vector\scripts\Invoke-LGKVector.ps1" `
  -ProjectPath "目标 DaVinci Cfg 绝对路径" `
  -Request '一条 JSON 请求'
```

请求很长时可以保存成 UTF-8 JSON 文件：

```powershell
& "D:\Tools\LGK-Vector\scripts\Invoke-LGKVector.ps1" `
  -ProjectPath "D:\Work\ProjectA\Cfg" `
  -RequestFile "D:\Temp\lgk-request.json"
```

包装器负责：校验 JSON、把内联请求写入 UTF-8 临时文件、启动或复用 resident host、调用 Rust 程序，并只删除自己创建的临时请求文件。

## 5. 请求格式和函数速查

每个请求都是一个 JSON 对象，至少包含 `func`：

```json
{"func":"find_module","module":"Com"}
```

| 函数 | 主要用途 | 是否修改 ECUC | 是否启动 DaVinci |
| --- | --- | --- | --- |
| `find_module` | 找模块配置文件和真实定义路径 | 否 | 否 |
| `inspect_ecuc_containers` | 读取已保存的容器和值 | 否 | 否 |
| `find_module_template` | 查看轻量容器/参数/引用层级 | 否 | 否 |
| `get_param_definition` | 查询少量参数定义 | 否 | 否 |
| `locate_container` | 定位容器和行号 | 否 | 否 |
| `edit_file` | 最小行或行范围替换 | 是 | 否 |
| `get_errors_list` | 获取 DaVinci 校验错误 | 否 | 是 |
| `auto_solve_errors` | 执行已确认的自动求解 | 可能 | 是 |
| `generate_code` | 生成模块或全部代码 | 否，产生生成输出 | 是 |
| `update_project` | 按 DPA 已登记输入执行 Project Update | 可能 | 是 |
| `import_dbc` | 替换已登记 DBC 并执行 Project Update | 是 | 是 |
| `shutdown_host` | 正常结束常驻会话 | 否 | 关闭已启动会话 |

兼容旧自动化的别名：`find_bsw_module`、`get_bsw_module_template`、`get_bsw_param_definition`。新请求使用表中的正式名称。

## 6. 各函数详细用法

### 6.1 find_module：找到真实模块

```json
{"func":"find_module","module":"Com"}
```

返回重点：

- `configPath`：该模块实际 ECUC ARXML；
- `definition_ref`：当前工程真实的模块定义路径；
- `module`：DPA 中识别到的模块名。

列出 DPA 中全部模块：

```json
{"func":"find_module","module":"all"}
```

模块名使用 `Com`、`CanIf`、`PduR` 这样的短名，不要传文件路径或 definition ref。

### 6.2 inspect_ecuc_containers：快速查看当前配置

按容器定义末段匹配：

```json
{
  "func": "inspect_ecuc_containers",
  "module": "Com",
  "container": "ComSignal",
  "short_name_regex": "^VehicleSpeed$",
  "params": ["ComBitPosition", "ComBitSize"]
}
```

也可以使用完整定义引用：

```json
{
  "func": "inspect_ecuc_containers",
  "module": "Com",
  "definition_ref": "/MICROSAR/Com/ComConfig/ComSignal",
  "params": "ComBitPosition,ComBitSize"
}
```

要求：

- `module` 必填；
- `container` 和 `definition_ref` 至少提供一个；
- `short_name_regex` 可选，默认匹配所有短名；
- `params` 可用字符串或字符串数组；不传时返回该容器能读取到的全部直接参数和引用值。

返回的 `container_path` 是实例路径，`definition_ref` 是模板定义路径，两者不要混淆。

它只读取已保存到磁盘的 ECUC ARXML，不启动 DaVinci，所以 GUI 打开并锁住 `.dpa` 时仍可用。但 GUI 中尚未保存的修改不会出现在结果里。

多条只读检查可以组成数组，结果会合并为一个扁平数组：

```json
[
  {"func":"inspect_ecuc_containers","module":"Com","container":"ComSignal","short_name_regex":"^SignalA$"},
  {"func":"inspect_ecuc_containers","module":"Com","container":"ComSignal","short_name_regex":"^SignalB$"}
]
```

不要在同一个批次中把 `inspect_ecuc_containers` 与其他函数混合。

多项请求数组只允许只读操作。`edit_file`、`auto_solve_errors`、`generate_code`、`update_project`、`import_dbc` 和 `shutdown_host` 必须分别单独发送，避免后续请求失败时留下前一项已经写入或生成的半完成状态。

### 6.3 get_param_definition：查询参数定义

```json
{
  "func": "get_param_definition",
  "module": "Com",
  "params": "ComBitPosition,ComBitSize"
}
```

这里的 `params` 必须是逗号分隔字符串，不是 JSON 数组。返回内容用于确认：

- 完整 `definition_ref`；
- 参数类型；
- ARXML 中应该使用的 value tag；
- 默认值、最小值、最大值和描述（模板提供时）。

已知参数名时优先使用这个函数，不要先读取整个模块模板。

### 6.4 find_module_template：查看轻量模块模板

```json
{"func":"find_module_template","module":"Com"}
```

默认返回模板文件、container/parameter/reference 数量，以及嵌套容器树中的直接参数和引用名称。它不会把每个定义的长描述、范围全部灌入上下文，适合下面场景：

- 不知道目标 container 或 parameter 名；
- 需要理解父子容器层级；
- 准备新增未知 container 或 reference。

如果维护者明确需要完整扁平定义，可单次传入：

```json
{"func":"find_module_template","module":"Com","details":true}
```

普通修改不要使用 `details:true`；已知名称时改用 `get_param_definition` 精确查询。

如果只查一两个参数，使用 `get_param_definition` 更快。

### 6.5 locate_container：定位实例和行号

```json
{
  "func": "locate_container",
  "module": "Com",
  "definition_ref": "/MICROSAR/Com/ComConfig/ComSignal",
  "short_name_regex": "^VehicleSpeed$"
}
```

`definition_ref` 必须使用查询返回的真实值，不要手写供应商前缀。返回：

- 实际 ECUC 文件；
- 匹配数量；
- short name；
- 容器实例路径；
- `start_line` 和 `end_line`。

`short_name_regex` 可为空；也可用逗号分隔多个正则。修改前应立即重新定位，因为文件变化后旧行号可能失效。

### 6.6 edit_file：执行最小修改

单行替换示例：

```json
{
  "func": "edit_file",
  "path": "D:\\Work\\ProjectA\\Cfg\\Config\\ECUC\\Vehicle_Com_ecuc.arxml",
  "expected": {
    "245": "                <VALUE>4</VALUE>"
  },
  "edits": {
    "245": "                <VALUE>8</VALUE>"
  }
}
```

行范围替换示例：

```json
{
  "func": "edit_file",
  "path": "D:\\Work\\ProjectA\\Cfg\\Config\\ECUC\\Vehicle_Com_ecuc.arxml",
  "expected": {
    "245-247": "                <VALUE>4</VALUE>"
  },
  "edits": {
    "245-247": "                <VALUE>8</VALUE>"
  }
}
```

要求和保护：

- `path` 必须是绝对路径，并且文件必须位于当前 `project_path` 内；
- `edits` 的键是单行号或 `起始行-结束行`；
- `expected` 必须使用与 `edits` 完全相同的键，并保存刚读取到的完整原文；
- 值是替换后的完整文本，可包含换行；
- 范围不能越界或互相重叠；
- 工具保留 UTF-8 BOM、CRLF/LF 和文件末尾换行；
- 若当前原文与 `expected` 不一致，工具拒绝写入，避免旧行号改错位置。

因此正确顺序是：先保存并关闭 DaVinci GUI 中的同一工程，再 `locate_container`，查看目标原文，确认行号，然后立刻 `edit_file`。LGK-Vector 会先正常关闭自己先前通过 `get_errors_list` 或生成请求打开的 DaVinci 会话，再写磁盘。GUI 打开时只做只读检查；否则 GUI 的内存模型仍可能在后续保存时覆盖外部 ARXML 修改。不要凭历史行号修改，也不要用这个函数做全文件机械重写。

### 6.7 get_errors_list：读取 DaVinci 错误

```json
{"func":"get_errors_list","module":"Com"}
```

读取全部模块：

```json
{"func":"get_errors_list","module":"all"}
```

该请求会启动 DaVinci 自动化会话。优先在受影响模块生成失败后调用，不要把全工程错误扫描当成每次查询的固定步骤。

### 6.8 auto_solve_errors：执行已确认的自动求解

```json
{
  "func": "auto_solve_errors",
  "module": "Com",
  "confirmed": true
}
```

必须先读取一份新的错误列表，理解 DaVinci 准备执行的动作，并获得明确确认。没有 `confirmed:true` 时工具直接拒绝。不要为了省时间盲目自动求解全工程错误。

### 6.9 generate_code：生成代码

只生成受影响模块：

```json
{"func":"generate_code","module":"Com"}
```

明确需要全量生成时：

```json
{"func":"generate_code","module":"all"}
```

单模块生成使用当前工程读取到的真实 `ECUC-MODULE-DEF`，不依赖固定芯片或固定 `/MICROSAR/` 路径。

生成会改变目标工程的生成目录，但不会把这些文件复制到其他编译工程。公司流程需要 Compare 时，仍要人工核对并按既定方向同步。

### 6.10 update_project / import_dbc：更新工程通信输入

工程中的 DBC 已经是正确内容，只需要按 DPA 登记关系重新同步时：

```json
{"func":"update_project"}
```

用一份新 DBC 替换 DPA 已登记的旧输入并同步时：

```json
{
  "func": "import_dbc",
  "source": "D:\\Matrix\\Vehicle_2026.dbc",
  "registered_path": "DBC\\Vehicle.dbc"
}
```

`source` 必须是存在的绝对 `.dbc` 路径；`registered_path` 必须位于当前 `Cfg` 目录内，而且已经作为 DPA 输入登记。工具不会猜测新增 ECU、通道或 DPA 文件项。调用成功会返回退出码、毫秒耗时、转换器错误/警告数和两份日志路径。调用前 LGK-Vector 会快照完整 Cfg；调用失败返回非零错误，并把 DPA、ARXML、DBC、日志以及本次新增文件一起恢复，失败诊断日志单独留在系统临时目录。

这两个函数都调用 DaVinci 官方 Project Update，不通过文本方式改 ARXML。执行前必须保存并关闭同一 DaVinci 工程。Project Update 成功表示通信描述完成同步，不等于生成 C/H/LSL；后续仍应读取错误列表并只生成受影响模块。

### 6.11 shutdown_host：正常结束会话

```json
{"func":"shutdown_host"}
```

每次完成请求后都执行。切换到另一个工程前也必须先关闭当前 host。不要用任务管理器强杀代替正常关闭。

包装器发现 host 已经不存在时，不会为了执行关闭而重新启动一个 host。

## 7. 一次完整的 ECUC 修改流程

下面以修改 COM Signal 的 `ComBitPosition` 为例。实际参数、definition ref、路径和行号必须来自目标工程查询结果。

### 第一步：记录目标工程 Git 状态

确认当前未提交改动，避免把别人的配置、生成代码或编译产物混入本次任务。不要 reset 或 clean 用户已有改动。

### 第二步：确认 COM 模块

```json
{"func":"find_module","module":"Com"}
```

保存返回的 `configPath` 和 `definition_ref`。

### 第三步：确认参数定义

```json
{"func":"get_param_definition","module":"Com","params":"ComBitPosition"}
```

查看参数类型、范围、描述和完整定义路径。

### 第四步：读取当前配置值

```json
{
  "func": "inspect_ecuc_containers",
  "module": "Com",
  "container": "ComSignal",
  "short_name_regex": "^目标Signal短名$",
  "params": ["ComBitPosition"]
}
```

确认只匹配一个预期容器，并记录当前值和 `container_path`。

### 第五步：定位准确行号

```json
{
  "func": "locate_container",
  "module": "Com",
  "definition_ref": "上一步查询得到的完整ComSignal定义路径",
  "short_name_regex": "^目标Signal短名$"
}
```

查看返回行范围附近的原始 ECUC 内容，找到需要替换的具体 VALUE 行。

### 第六步：最小修改

用刚确认的绝对文件路径和行号调用 `edit_file`。只替换目标行或必要的最小范围。修改后再次读取目标区域，确认没有改变相邻 container。

### 第七步：只生成 Com

```json
{"func":"generate_code","module":"Com"}
```

生成成功表示 DaVinci 接受了这次 ECUC 配置，但不等于实车通信一定正确。

### 第八步：检查两类差异

分别检查：

1. ECUC 配置差异：哪个 container、parameter 或 reference 改了；
2. 生成输出差异：哪些 C/H/LSL 因这次配置重新生成。

如果公司工程从配置工程的 `Gen` 单向 Compare 到编译工程，只同步确认属于本次配置的生成结果。Callout、回调桩和人工修改过的生成骨架必须单独比较，不能整目录覆盖。

### 第九步：失败时再查错误

受影响模块生成失败后调用 `get_errors_list`。先读错误，再决定人工修复或是否允许 `auto_solve_errors`。

### 第十步：正常关闭

```json
{"func":"shutdown_host"}
```

最后只暂存和提交本次涉及的 ECUC、生成输出和业务代码。

## 8. ECUC 配置、生成代码和编译产物的区别

| 类型 | 常见位置或后缀 | 含义 | 一般处理方式 |
| --- | --- | --- | --- |
| ECUC 配置 | `Cfg\Config\ECUC\*.arxml`、`.dpa` | DaVinci 工程中配置了什么 | 通过 LGK-Vector/DaVinci 修改和校验 |
| 生成输出 | `Gen\*.c`、`*.h`、`*.lsl` | ECUC 配置的工具生成结果 | 生成后 Compare，按工程规则同步 |
| 业务代码 | ASW、Callout、回调实现 | 人工实现的功能逻辑 | 单独审查和提交 |
| 编译产物 | `.o`、`.elf`、`.hex`、`.map` | 编译链接结果 | 通常不反向同步到生成目录 |

不要直接修改生成的 C/H/LSL 来冒充 ECUC 修复。下次 DaVinci 生成会覆盖这种修改，而且 Config 中看不到真实变化。

## 9. 常见问题排查

### 找不到 lgk-vector.exe

在中央目录执行 `cargo build --release --locked`，确认 `target\release` 中同时存在 CLI 和 host 两个程序。

### 找不到 lgk-vector.json

`-ProjectPath` 必须指向 DaVinci Cfg 目录本身，不是工程根目录，也不是 `Config\ECUC` 子目录。

### project_path 不匹配

新配置可省略 `project_path`。旧配置若保留该字段，必须与包含 JSON 的目录完全一致；不要借用另一个工程的配置文件。

### 找到多个 DPA 或多个 DVCfgCmd.exe

在 `lgk-vector.json` 中明确设置 `project_file` 或 `davinci_command_path`，不要让工具猜选哪一个。

### DaVinci 提示 .dpa 被其他程序锁定

- `inspect_ecuc_containers`、`find_module`、参数定义和定位等本地操作仍可使用；
- `edit_file`、`get_errors_list`、`auto_solve_errors`、`generate_code`、`update_project` 和 `import_dbc` 前都应保存并关闭 GUI 中打开的同一工程；GUI 打开时只使用只读检查；
- 错误信息会保留本次临时日志目录，供进一步诊断。

### 查询结果为空

依次检查：模块短名、完整 definition ref、short name 正则、参数名，以及 GUI 中修改是否已经保存到磁盘。可以先用 `find_module`，再用 `get_param_definition` 或 `find_module_template` 缩小范围。

### 生成成功但总线仍不通信

生成成功只证明 ECUC 被 DaVinci 接受。还要检查发送或接收链路中的 RTE/SWC、COM、PduR、CanIf、CAN Driver、HTH/HRH、收发器、线束、终端电阻和总线测量结果。COM 不直接引用 HTH/HRH。

### host 长时间未退出

先发送 `shutdown_host`。如果返回超时，记录错误和 runtime 目录，不要立即通过任务管理器反复强杀并重启多个会话。

## 10. 更新和维护中央工具

实际工程暴露工具问题时：

1. 使用 `$lgk-vector`，Codex 会通过 Junction 进入中央源码；
2. 查看 `CHANGELOG.md`，确认当前版本和已知限制；
3. 本地 ECUC 操作查看 `src\ops`，resident host 和 DaVinci 协议查看 `src\app`、`src\daemon`，包装器查看 `scripts`；
4. 使用公开、虚构的最小 ECUC 测试夹具复现；
5. 修改源码并补测试；
6. 运行 `cargo test --all-targets --locked`；
7. 发布前运行 `cargo build --release --locked`；
8. 在 `CHANGELOG.md` 写明日期、提交、问题、验证和限制；
9. 只在中央源码 Git 仓库提交工具改动。

其他 AUTOSAR 工程不需要复制或同步工具文件。中央版本更新后，所有工程下一次调用都会使用新版本。

## 11. Git 与资料边界

中央 LGK-Vector 仓库保存：

- Rust 源码；
- Skill；
- PowerShell 脚本；
- 可公开测试；
- 使用说明和更新记录。

各 AUTOSAR 工程保存：

- 自己的 `lgk-vector.json`；
- ECUC 配置；
- DaVinci 生成的 C/H/LSL；
- 业务代码。

不要把客户 DPA/ARXML/DBC、Vector SIP、许可证、原厂文件、反编译产物、账号、Token 或客户生成代码提交到中央工具仓库。工具变更和 AUTOSAR 工程变更分别提交，不要混成一个 Git 提交。
