# LGK-Vector 开源前快速上手

这份说明只讲最常用的内容：工具在做什么、怎样跑一次、怎样判断成功，以及发布到 GitHub 前要检查什么。

## 1. 先记住两个概念

ECUC 配置和生成代码不是同一种东西：

- `.dpa`、ECUC ARXML 是 DaVinci 工程配置，决定模块中配置了什么。
- `generate_code` 生成的 `.c`、`.h`、`.lsl` 是配置的输出，供编译工程使用。

不要为了改变配置而直接改生成的 C/H/LSL。正确顺序是修改 ECUC 配置，再让 DaVinci 重新生成。如果公司流程要求 Compare，同步的是确认过的配置和生成结果；`.o`、`.elf`、`.hex`、`.map` 等编译产物一般不参与反向同步。

## 2. 这个工具怎样找到模块

它按下面的关系自动查找：

```text
DPA 工程文件
  → 找到模块对应的 ECUC ARXML
  → 读取真实 ECUC-MODULE-DEF 路径
  → 在当前 SIP/BSWMD 中找到定义
  → 定位参数、容器并调用对应生成器
```

所以它不依赖 TC275，也不要求模块定义一定以 `/MICROSAR/` 开头。真正决定能否使用的是：DaVinci、目标工程和 SIP 是否互相匹配。

## 3. 第一次配置

普通使用者优先从 GitHub Release 下载 `windows-x64.zip` 并解压到 `D:\Tools\LGK-Vector`。发布包已经带有版本一致的 CLI/Host，不需要先安装 Rust；只有从源码开发、修改或自行编译时才需要 Rust。

推荐让脚本建立配置并立即做静态预检：

```powershell
& .\scripts\Initialize-LGKVectorProject.ps1 `
  -ProjectPath "D:\Work\MyProject\Cfg" `
  -ToolPath "D:\Vector\SIP"
```

最小 `lgk-vector.json` 只需本机工具路径；工程路径由 JSON 所在目录推导：

```json
{
  "tool_path": "D:\\Vector\\SIP"
}
```

如果目录中有多个 DPA，或者安装目录下能找到多个 `DVCfgCmd.exe`，再加两个可选字段：

```json
{
  "tool_path": "D:\\Vector\\SIP",
  "project_file": "VehiclePlatform.dpa",
  "davinci_command_path": "D:\\Vector\\DaVinci\\Exec\\DVCfgCmd.exe"
}
```

两个程序 `lgk-vector.exe`、`lgk-vector-host.exe` 要放在同一个目录。推荐始终通过 `scripts/Invoke-LGKVector.ps1` 调用。

静态预检只检查 JSON、工程文件、模块定义和 DaVinci 命令路径，不会启动 DaVinci。它通过不等于许可证、工程锁和真实生成已经验证；后者必须使用合法且可丢弃的 DaVinci 测试工程确认。

## 4. 先做一次只读测试

把下面的路径换成自己的 `Cfg` 目录：

```powershell
& .\scripts\Invoke-LGKVector.ps1 `
  -ProjectPath "D:\Work\MyProject\Cfg" `
  -Request '{"func":"find_module","module":"Com"}'
```

成功时会返回三项重要信息：

- `configPath`：COM 实际配置文件。
- `definition_ref`：当前 SIP 中 COM 的真实模块定义路径。
- `module`：识别到的模块名。

这一步只查找，不修改配置，也不生成代码。

## 5. 修改一次配置的正确顺序

以 COM 参数为例：

1. 用 `find_module` 找实际模块文件。
2. 用 `get_param_definition` 查参数类型、范围和定义路径。
3. 用 `locate_container` 找实际容器与行号。
4. 保存并关闭 DaVinci GUI 中的同一工程，查看目标位置的当前内容，并把原文放入 `edit_file.expected`；原文变化时工具会拒绝写入。
5. 调用 `generate_code`，只生成受影响的模块。
6. 仅当生成失败时，再调用 `get_errors_list`。
7. 工作结束后调用 `shutdown_host`。

查询一个参数：

```powershell
& .\scripts\Invoke-LGKVector.ps1 `
  -ProjectPath "D:\Work\MyProject\Cfg" `
  -Request '{"func":"get_param_definition","module":"Com","params":"ComBitPosition"}'
```

生成 COM：

```powershell
& .\scripts\Invoke-LGKVector.ps1 `
  -ProjectPath "D:\Work\MyProject\Cfg" `
  -Request '{"func":"generate_code","module":"Com"}'
```

正常关闭：

```powershell
& .\scripts\Invoke-LGKVector.ps1 `
  -ProjectPath "D:\Work\MyProject\Cfg" `
  -Request '{"func":"shutdown_host"}'
```

不要用任务管理器强制结束 resident host。也不要在没有看过当前错误和影响时直接运行自动修复。

## 6. 怎样判断一次修改完成了

至少确认下面四项：

1. `edit_file` 只改了预期的 ECUC 文件和行。
2. `generate_code` 返回 `OK: generation completed`。
3. Git 差异中，ECUC 配置变化与生成的 C/H/LSL 变化能够对应起来。
4. resident host 已通过 `shutdown_host` 正常关闭。

DaVinci 生成成功表示 ECUC 配置被工具链接受，但不等于实车通信一定正常。CAN 通信仍要继续检查 MCAL、CanIf、PduR、COM、RTE、收发器、线束和总线测量结果。

## 7. 发布到 GitHub 前检查

先不要急着上传，逐项确认：

- 仓库中没有客户 ARXML、DPA、DBC、生成代码、日志和工程截图。
- 没有 Vector 安装包、SIP、许可证、原厂二进制或反编译输出。
- 没有公司名称、账号、内网地址、Token、邮箱和绝对工程路径。
- `git log` 中的作者姓名和邮箱适合公开；Git 提交历史也会随仓库一起发布。
- 内部开发历史含个人邮箱或旧产品名时，不直接推送该历史；从审核后的当前树建立干净根提交，并用 GitHub noreply 身份发布。
- `cargo test --all-targets --locked` 能通过。
- `cargo build --release` 能成功生成两个程序。
- 两个程序的 `--version` 输出完全一致；不要把旧二进制与新脚本混在同一发布包中。
- `Cargo.toml` 中补上真实的 GitHub `repository` 地址。
- README、LICENSE、NOTICE 与实际功能一致。
- 源码提交到仓库；自己编译的 `.exe` 更适合放到 GitHub Release，不要混入源码提交。

完成检查后，再建立 GitHub 仓库、添加远程地址并推送。首次公开建议先使用私有仓库自查一遍，确认下载、编译、运行和关闭流程都正常，再切换为 Public。

## 8. 当前边界

这个项目解决的是 Vector DaVinci ECUC 工程的本地自动化，不是通用 ARXML 编辑器，也不替代 DaVinci 许可证。所谓“通用”是指不绑定某一款 MCU、某一个项目名或某一个模块定义前缀；它仍然依赖 Vector DPA 工程结构和 DaVinci Automation Interface。
